# Finish a request after building a tool

A missing function can interrupt useful work. In 0.16, Companion keeps your original request separately from the AI’s implementation instructions when a chat or voice task starts a feature build.

1. **Ask for the outcome in Chat or by voice.** If a missing function needs building, open its linked **View feature build** action. The build shows the exact **Your request** and separate **Build instructions** in expandable sections.
2. **Review and activate the build.** Inspect its actual changes and checks. Use **Activate feature** when review is required, and wait for any service restart and readiness check.
3. **Choose Continue original request.** It appears only when the saved request is ready. Or keep that build selected and say exactly “continue original request.” The command does not apply to a different build selected after recording starts.
4. **Open work to inspect the result.** This is a separate job, so your foreground chat stays available. Its actual action receipts show what finished, failed or still needs review.

Building or activating a tool never automatically resumes the task. A direct Build form request or external patch is a source change without an attached human task; it does not create a Continue action.

An ordinary build still follows its normal verification and activation rules. Protected changes require review of the concrete diff and explicit activation. After activation, server changes need the appropriate service restart. **Continue original request** becomes available only when current source hashes and the loaded callable capability match the applied build. A mounted panel or an old Activated label alone is insufficient. A panel-only build retains its Open action; it does not pretend to supply a callable tool for a follow-through run.

Choose **Continue original request**, or open that build and say “continue original request.” The spoken command captures the selected build before microphone permission and refuses a later selection. Companion starts one linked Work job using the original request, provider configuration, project grant and window selection. It preserves the current foreground chat and shows the actual job through **Open work**. The model-written implementation spec never replaces the human’s goal.

Completed original actions are supplied as prior receipts. Exact repeated mutations reuse those receipts, including workspace actions inside a capability, rather than performing the same effect twice. The interface labels these **Already completed earlier** instead of claiming a new save. Abbreviated, pending or uncertain original action records prevent continuation. This pass cannot start another feature build or delegate further work. A completed result must include an actual successful execution receipt from one of the newly installed capabilities. A model’s statement of success is insufficient.

The new job keeps the saved request and original provider configuration, project access and window selection. Choosing another AI or folder in the foreground does not retarget it. Changing the original provider configuration, revoking that project grant, losing its selected window, rolling back source, or changing a required tool prevents a new start. A window pin lost during restart cannot silently become a different window. Start a new explicit request after selecting the intended source when that happens. The original task remains reviewable.

One original request has one reserved build and one reserved follow-through Work identity. Repeated clicks, a lost acknowledgement and restarts inspect that same identity; they never create another continuation or replay uncertain effects. **Check continuation** performs only a read, including after reloading the page or choosing another build. It never resends the task. An explicit check that confirms Ready before any Work acceptance permits a new deliberate Continue action with the same ID. If a spoken Continue loses its response, voice turns off while this check remains available. Stop cancels pending admission and dependent Work; completed receipts remain. A failed or interrupted continuation is retained for inspection rather than automatically tried again.

The initial release uses an explicit Continue action after installation. It does not automatically run old intentions when the app starts. Direct build-form and external patch requests remain source-development operations unless they originated from a linked chat/voice task. Multiple tools needed by one request should be implemented in one coherent build; a second different build specification for the same original receipt is refused before generation.

External AI clients can inspect a linked continuation through `inspect_feature_build`, then request its one continuation through `manage_work` with `{action:'continue',continuationId}` when the human asks to finish that task. This uses the same runtime and permission checks. Private continuation state lives beside the app’s other data, outside source. Browser storage retains only pending continuation IDs, never the task text, file roots or credentials.
