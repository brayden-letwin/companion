# Product direction and requirement evidence

## The full goal

Companion should be a simple, beautiful personal assistant that understands a spoken intention, helps get useful work done, and grows when it is missing a needed capability. The current accepted direction is **general productivity first**, inspired by Jarvis. It should connect to GPT/Codex, Claude, and other suitable AIs, and let authorized AI tools improve the actual program rather than merely suggesting code in a chat.

The app should stay easy to open and easy to talk to. It should support several things happening at once, show what it is actually doing, and give the user a clear way to stop, inspect, activate, or undo work. Missing features should lead to a real implementation workflow with source changes, checks, and a usable result. A small set of built-in task tools is a starting point, not a reduction of that goal.

Earlier math-reading and University of Washington theory-group requirements remain part of the history. Math is currently secondary. General intended computer actions, voice-driven development, broader AI-client connections, and broader native interaction remain goals where the present implementation is incomplete. The general native corner and a scoped Windows action service are now implemented; they do not complete every PC-control or voice-development requirement.

This document records scope and evidence. It does not grant a model unlimited PC access, create an institutional affiliation, or make a proposed capability an implemented one.

## How the assistant should behave

- Keep the main request box simple: “What do you want to get done?” Use context and tools when they are relevant.
- Reuse a working capability before rebuilding it. A missing capability should produce a useful, scoped build request with observable acceptance criteria.
- Ground statements about completed work in actual receipts. Preserve partial results and state when a request fails or is cancelled.
- Keep plans, queued builds, verified candidates, activated code, and working behavior distinct. Show actual progress rather than invented percentages or reasoning logs.
- Preserve the selected provider and request input for the duration of a turn. Do not let navigation or late asynchronous results silently retarget the user's intention.
- Keep keys and private runtime data out of source, prompts, logs, and browser storage. External AI receives only the context deliberately provided through its request/tool workflow.
- Let the user inspect and undo source changes. If later edits prevent a safe rollback, report the conflict rather than overwriting them.
- Add capabilities without turning the interface into an overwhelming dashboard. Registered panels should remain discoverable by navigation and eventually by voice.

## What still makes the full goal incomplete

1. **Live account and client connections.** Explicit fixed checks now have real Codex and local Ollama evidence, with saved revisions and truthful historical results. Claude and optional API providers still need user-owned keys and live checks; a passed completion alone does not verify tool use or feature generation. External Codex source editing has a real isolated build/UI/rollback proof; Claude and other clients still need explicit setup and verified task/build results.
2. **The exact voice-development bridge.** The user asked to speak commands into this existing Codex chat. The present general assistant talks to its own selected provider; saved conversations preserve intent across Companion windows and MCP clients. A read-only probe of the installed Codex app-server proxy and daemon version could not connect to its default local control socket (Windows error 10050). No competing daemon was started and no message was injected. The exact existing-chat route remains open.
3. **Broader actions beyond the scoped Windows tools.** Explicit window reads and a reviewed-input service now exist, and app search/open has live proof. A real Notepad text-input outcome has also been verified. More applications and input patterns, calendar/mail/file integrations, and broader reliable context still need real adapters and verification.
4. **A dependable adaptive program.** Executable capabilities have actual-code acceptance cases, guarded runtime limits and immutable workflow receipts. Full service-host changes now have live restart and cached-source recovery proof, while control-kernel changes use explicit Stop/Start. Linked build follow-through retains original intent and admits one explicit Work run only after source/tool/runtime proof, with prior-effect reuse and actual capability receipt checks. Generated candidates can receive one bounded correction after failed checks, with immutable attempt history, the same source/provider/request and frozen initial acceptance contracts. An isolated seeded failure received a real GPT correction and passed live use/rollback checks. Broader generated UI acceptance, live user-requested features, data/schema migrations, recovery across future journal-format changes and long-term maintenance still need work. Automatic ordinary changes alone do not establish reliable self-programming.
5. **Everyday voice and multitasking.** The native corner was observed and basic voice success was user-reported. Independent Work jobs now have real GPT/MCP/browser evidence, retained outcomes, isolated intent, and cancellation. After a fresh native launch, physical global Stop cancelled a pending Notepad action while leaving existing text unchanged. Renderer-failure recovery has automated coverage rather than a physical failure-injection check. Human spoken job coordination, desktop approval, interruption, difficult audio conditions, shortcut conflicts, longer sessions and multi-monitor behavior still need product validation.
6. **Distribution and durable operation.** Conversation turns, actual action results, and explicitly taught preferences persist locally. Workspace-content JSON backup and selected-copy recovery have browser/restart evidence; full installation/build-history recovery, scheduled backups, migration, signing/updates and remote access where desired remain unfinished.
7. **The earlier collaboration branch.** Remote theory-group use needs hosting, real papers, source permissions/anchors, membership/recovery decisions, and group testing.

Do not mark the overall product complete because tasks, notes, a provider adapter, or a source-patching API works. Those are concrete advances toward the full intention.
